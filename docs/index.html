How the Pharma Rep Copilot works

A hybrid retrieval system that answers pharma sales-rep questions by routing each one to the right data path — sales database, support documents, or both — and stitching one cited answer with Claude. This page walks through every component, what it sends and receives, and how a question flows end-to-end.

GitHub: supriyamalla/hybrid-rag-model →

Architecture at a glance

Three classes of question, three paths through the system. The router decides which path(s) a question needs; the orchestrator runs them and hands the results to Claude for synthesis. Click any node to jump to its module.

The three routes

Every question goes through the same router and gets exactly one of these labels. The label decides which agents fire and what the synthesis prompt sees.

analytical  Numbers from the sales database

"What was total revenue by product in the Northeast?"

The router sees performance / revenue / region terms. It returns:

// router output
{
  "route": "analytical",
  "filters": { "product": null, "region": "Northeast", "doc_type": null },
  "reasoning": "asks for aggregate revenue numbers; sales DB only."
}

needs_sql = true, needs_docs = false. The orchestrator calls only the SQL agent. The semantic layer is rendered into the SQL prompt, Sonnet generates a single SELECT, the validator checks it's read-only, the connector executes it against the SQL warehouse. Synthesis cites the SQL result with [SQL].

knowledge  Facts from support docs

"How does prior authorization work for Oncorix?"

The router sees a policy / process question naming a product:

// router output
{
  "route": "knowledge",
  "filters": { "product": "Oncorix", "region": null, "doc_type": "prior_auth" },
  "reasoning": "PA process for a specific product → support docs."
}

needs_sql = false, needs_docs = true. The RAG agent receives the three filters and passes them to Vector Search's filters={...} arg, so retrieval is semantic search constrained by BI metadata. Chunks below SIMILARITY_THRESHOLD are dropped. Synthesis cites each fact with [<doc_id>].

hybrid  Numbers + docs, merged with citations

"Cardiozen Q3 2025 attainment in the Northeast — and what's the formulary situation?"

The router sees both an analytical clause and a policy clause:

// router output
{
  "route": "hybrid",
  "filters": { "product": "Cardiozen", "region": "Northeast", "doc_type": "formulary" },
  "reasoning": "performance question + formulary question, same scope."
}

needs_sql = true AND needs_docs = true. Both agents fire with the same filter scope. The synthesis prompt receives a SQL result block AND a chunks block, and Claude weaves them — typical output looks like: "Cardiozen attainment was 40.3% [SQL], below target despite Tier-2 commercial placement [FORM-CARDIOZEN-NE]."

One public function: answer(question) → CopilotResult. Calls the router, then conditionally runs the SQL agent and/or the RAG agent based on needs_sql / needs_docs. Wraps SQL failures so the docs path can still answer. Builds a single context block and asks Claude Sonnet for the final answer with hard requirements: only state facts present in the context, cite every claim, no preamble.

Why this is the differentiator. A naive RAG bot embeds the question and does top-K cosine over everything. This router (a) decides which data path even applies, and (b) extracts BI filters that constrain retrieval to the right scope. Same vector similarity, narrower candidate set — semantic search constrained by structured metadata.

The SQL agent is generic Text-to-SQL — what makes it correct on this business is the context this file renders. Update this file when BI definitions change; never the agent. Also exports the canonical vocabularies the router uses.

Exports
  • get_schema_context(scope) → full prompt context
  • KNOWN_PRODUCTS, KNOWN_REGIONS, KNOWN_DOC_TYPES
Contents of the rendered context
  • Table descriptions (columns, sizes, join FKs)
  • Metric formulas (revenue, target attainment)
  • Disambiguation rules ("this quarter" → Q4 2025, etc.)
# When user scope is known, append it as a hint.
def get_schema_context(scope: dict | None = None) -> str:
    parts = [TABLES, METRICS, DISAMBIGUATION]
    if scope:
        hints = [f"- {k}: {v}" for k, v in scope.items() if v]
        parts.append("Router-extracted scope:\n" + "\n".join(hints))
    return "\n".join(parts)

Builds a system prompt from get_schema_context(scope), asks Sonnet for exactly one Spark SQL SELECT, validates it's read-only (no DDL/DML, single statement), and executes via databricks-sql-connector. If generation, validation, or execution fails, the error is fed back to the model and the agent retries up to SQL_MAX_ATTEMPTS times.

Inputs
  • question: str
  • scope: dict — router-extracted filters
Returns
  • {sql, columns, rows}
  • Raises if all retries fail
for attempt in range(config.SQL_MAX_ATTEMPTS):
    try:
        sql = generate_sql(prompt, scope)         # Sonnet call
        columns, rows = _execute(sql)              # SQL warehouse
        return {"sql": sql, "columns": columns, "rows": rows}
    except Exception as e:
        prompt = _retry_prompt(question, sql, e)  # feed error back, retry

End-to-end trace: a hybrid question

Click through the steps below to follow one question — "Cardiozen Q3 2025 attainment in the Northeast — and what's the formulary situation?" — from rep input to cited answer. Each step shows what gets called, what goes in, what comes out.

1 Rep types the question in the chat

app/streamlit_app.py · st.chat_input → orchestrator.answer()

The Streamlit UI captures the input and calls orchestrator.answer(question) inside a spinner. No model calls have happened yet — this is just a function dispatch.

Input
"Cardiozen Q3 2025 attainment in the Northeast — and what's the formulary situation?"
Output
— (control flow passes to orchestrator)

2 Router classifies — Haiku call

app/router.py · classify() · model: claude-haiku-4-5

Haiku reads the question against the route definitions and canonical vocabularies in the system prompt, returns strict JSON. The Python validator drops anything not in the vocab, then bundles into a RouterDecision.

Input → Haiku
system: route definitions + KNOWN_PRODUCTS, KNOWN_REGIONS, KNOWN_DOC_TYPES user: "Cardiozen Q3 2025 attainment in the Northeast — and what's the formulary situation?"
Output
RouterDecision( route="hybrid", needs_sql=True, needs_docs=True, filters={ "product": "Cardiozen", "region": "Northeast", "doc_type": "formulary" }, reasoning="attainment number + formulary question, same scope" )

3 SQL agent — generate one SELECT

app/sql_agent.py · generate_sql() · model: claude-sonnet-4-6

The semantic layer renders the schema, metric formulas, and disambiguation rules. The scope is appended as a hint. Sonnet returns a single Spark SQL SELECT; the validator confirms it's read-only.

Input → Sonnet
system: TABLES + METRICS + DISAMBIGUATION + scope: - product: Cardiozen - region: Northeast user: "Cardiozen Q3 2025 attainment in the Northeast — and what's the formulary situation?"
Generated SQL (validated)
WITH actual AS ( SELECT SUM(s.revenue) AS actual_rev FROM workspace.pharma_sales.sales s JOIN workspace.pharma_sales.sales_reps sr ON s.rep_id = sr.rep_id JOIN workspace.pharma_sales.regions r ON sr.region_id = r.region_id JOIN workspace.pharma_sales.products p ON s.product_id = p.product_id WHERE LOWER(p.product_name)='cardiozen' AND LOWER(r.region_name)='northeast' AND QUARTER(s.sale_date)=3 AND YEAR(s.sale_date)=2025 ), tgt AS ( SELECT SUM(t.target_revenue) AS target_rev FROM workspace.pharma_sales.targets t JOIN workspace.pharma_sales.sales_reps sr ON t.rep_id = sr.rep_id JOIN workspace.pharma_sales.regions r ON sr.region_id = r.region_id JOIN workspace.pharma_sales.products p ON t.product_id = p.product_id WHERE LOWER(p.product_name)='cardiozen' AND LOWER(r.region_name)='northeast' AND t.year=2025 AND t.quarter=3 ) SELECT actual_rev, target_rev, actual_rev/NULLIF(target_rev,0) AS attainment FROM actual CROSS JOIN tgt LIMIT 100

5 RAG agent — filtered retrieval

app/rag_agent.py · retrieve() · Databricks Vector Search

The router's filters become Vector Search's filters argument. Only chunks where product=Cardiozen AND region=Northeast AND doc_type=formulary are eligible — and in this corpus, only one doc matches all three.

Input
query_text: "Cardiozen Q3 2025 attainment in the Northeast — and what's the formulary situation?" filters: { "product": "Cardiozen", "region": "Northeast", "doc_type": "formulary" } num_results: 5 threshold: 0.3
Output (after threshold filter)
[ RetrievedChunk( doc_id="CARDIOZEN-NORTHEAST-FORMULARY-STATUS", title="Cardiozen Northeast Regional Formulary Status", score=0.78, content="Cardiozen is on the preferred tier (Tier 2) for the three largest commercial payers..." ), RetrievedChunk(..., score=0.62) # second chunk of same doc ]

6 Synthesis — Sonnet writes the final answer

app/orchestrator.py · _synthesize_async() · model: claude-sonnet-4-6

The context block contains both the SQL result and the retrieved chunks (with their doc_id labels). The system prompt forbids unsupported claims and requires inline citations: [SQL] for numbers, [<doc_id>] for doc facts.

Input → Sonnet
system: cite every claim; only state facts in context user: REP QUESTION + CONTEXT === SQL RESULT === (query, columns, rows) === SUPPORT DOCUMENTS === [CARDIOZEN-NORTHEAST-FORMULARY-STATUS] (chunks)
Output (markdown with citations)
"Cardiozen Q3 2025 attainment in the Northeast came in at 40.3% ($14,387 actual / $35,717 target) [SQL]. Despite the gap, Cardiozen sits on Tier 2 (preferred) with the three largest commercial payers in the region [CARDIOZEN-NORTHEAST-FORMULARY-STATUS], suggesting the underperformance isn't formulary-driven. UnitedHealthcare and Aetna require step therapy through statins [CARDIOZEN-NORTHEAST-FORMULARY-STATUS], which may be slowing new starts despite favorable tier placement."

Data shapes that flow between components

Three small dataclasses carry everything. Each one is the contract between two layers.

RouterDecision

app/router.py — output of classify()

@dataclass
class RouterDecision:
    route: Literal["analytical", "knowledge", "hybrid"]
    needs_sql: bool
    needs_docs: bool
    filters: dict   # {product, region, doc_type}
    reasoning: str

RetrievedChunk

app/rag_agent.py — one per retrieved chunk

@dataclass
class RetrievedChunk:
    chunk_id: str
    doc_id: str
    title: str
    doc_type: str
    product: str | None
    region:  str | None
    content: str
    score:   float   # cosine similarity

CopilotResult

app/orchestrator.py — return value of answer()

@dataclass
class CopilotResult:
    question: str
    route: str
    reasoning: str
    filters: dict
    answer: str          # synthesized markdown
    sql: str | None
    sql_error: str | None
    columns: list[str]
    rows: list[tuple]
    sources: list[dict]    # [{doc_id, title, score}]

If you only remember three things

1. The router is the differentiator. It picks the route AND the filters that narrow retrieval. Same vector similarity, narrower set.

2. The semantic layer is the single source of business truth. Update semantic_layer.py — never the SQL agent — when BI definitions change.

3. The orchestrator never trusts the model with raw facts. It builds a context block with the SQL result and the retrieved chunks (each labeled with its doc_id), then forces Sonnet to cite every claim. If a fact isn't in the context, Sonnet can't say it without citing nothing.
